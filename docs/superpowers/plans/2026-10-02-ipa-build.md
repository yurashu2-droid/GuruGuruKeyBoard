# iOS IPA build implementation plan

Goal: produce a real ARM64 iPhoneOS IPA containing the keyboard extension and Japanese dictionary, not a renamed source archive.

Architecture: SwiftUI host + Custom Keyboard Extension, pinned azooKey 0.11.2 dictionary converter; GitHub Actions macOS Release archive. No signing secrets, network keyboard access, or learning storage.

1. Pin the dependency to an API-compatible release and isolate converter to MainActor. Pending kana stays in the keyboard until explicitly committed; never delete host text by guessing reading length. Test empty input, 日本, 東京 after reset, kana fallback.
2. Add a packaging validator and rejection tests for missing extension, dictionary, or device platform. Run failing tests before implementation, then all four passing. Package only the successful device archive. Include upstream license files.
3. Push the build/ios-ipa branch, run native Swift converter tests and Xcode archive, inspect errors and fix them, retrieve the resulting artifact and verify it. Report native and structural tests separately from real-device testing.

Constraints: iOS 16+, Swift tools 6.1+, Zenzai off, full access false. Unsigned IPA requires user-controlled re-signing of app and extension. Do not request or commit certificates/passwords.

Rulings: package version moved from incompatible 0.8.x to pinned 0.11.2. Input remains pending in the keyboard until commit to avoid destructive cursor/field mismatch. This MVP drops pending reading when an external host action hides or changes the input field. No independent reviewer or physical iPhone is available; document this verification limit.
